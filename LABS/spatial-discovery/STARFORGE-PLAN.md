# Starforge reuse investigation

Goal: test existing capabilities before designing replacements. All outputs and adapters stay in this lab. No changes to Starforge, Starship or client code. No harvest, model calls or deployment.

## Ranked checklist

1. Catalog coverage / export / health: distinguish missing inputs from inadequate algorithms.
2. Full concept search and lineage-aware explore: recover research destinations using the complete pipeline, not just BM25.
3. Repo and gem lineage / scaffolding: separate versions from numbered experiments and generic file names.
4. Polyglot token groups: recover auth/security versus unrelated feature areas from real source.
5. Import groups, then semantic groups: identify coherent multi-file packages; check whether a monorepo becomes one giant group.
6. Ancestry: test copied/evolved implementation matching; check whether results prove chronology or only resemblance.
7. Paradigms / entry points / API detection: provide descriptions and useful places to enter a product.
8. Captain's logs / why / profile / timeline: inspect preserved intent and actual date semantics.
9. Integrate only through lab adapters, compare findings and retain misses.

Read-only CLI tests use a private catalog copy and existing harvest files. Local-source tests use unchanged Starforge library functions on bounded file inventories. Timeouts are recorded as incomplete, not failures of classification. Synthetic fixtures are separate from real examples. Every trial records command/function, source, duration and outcome. Do not interpret a CLI exit code of zero as a useful answer.

Selection: current NavCom inventory and Syra B2B source for real inputs; unrelated synthetic products, named versions and numbered experiments for mechanism checks. No tuning thresholds after observing outcomes without recording a separate exploratory trial.
