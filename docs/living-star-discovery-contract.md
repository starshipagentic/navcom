## Minimal shared adapter contract

1. **Discover from existing inputs.** Native Hermes profiles come from its own inventory. Project-local candidates come from already discovered roots and bounded provider metadata: Compose service + verified Hermes image/entrypoint + OCI labels + charter/skills references. Do not require the string `semanticobservatory`, a known client folder, or a new hand-maintained registry. Do not execute Dockerfiles, bootstrap scripts or arbitrary commands found in README text.
2. **Return candidates with separate evidence levels.** A useful record has `provider`, `provider_identity` (profile ID/home, or repository + Compose file + service), `name`, `description`, `description_auto`, `charter_refs`, `steward_evidence`, `version_evidence`, `physical_binding`, `source_scopes`, `interfaces`, `observations`, `gaps`. Use current NavCom source IDs for document search. A description and runnable agent are grounds for a candidate; empty/missing ownership, unconfirmed prose and untested availability remain visible.
3. **Keep transport capabilities typed.** Each interface needs an existing argv or route template, exact cwd/container/profile binding, effect (`inspect`, `observe_status`, `ask_agent`, `submit_work`, `administer`), auth requirement without its value, source reference and verification state. Template values are data, never shell snippets. Host-local wrappers are not portable remote endpoints.
4. **Cache discovery and search separately from health.** Metadata fingerprints invalidate cached candidate descriptions; source search uses the existing harvest and query caches. Status is an explicit, bounded observation with its own time and result. Missing runtime remains `unknown`/`unobserved`, not `offline` or `available`. Browsing must not load the 27B brain or start a gateway.
5. **Link expertise without forced ownership.** Expose a star-role candidate as a distinct destination with evidence and existing capabilities. Keep it separate from its underlying product/repository and from solar-system ownership. Native assistant lists, tool packages and ordinary repositories do not automatically become stars.

## Implemented lab service and proof

[`navcom_stars.discover()`](/Users/t/dev/navcom/navcom_stars.py) is the bounded service. It accepts existing source records (`root`, optional `id`) or explicit roots and an optional native `profile_home`. It returns candidate DTOs, excluded entries, input coverage, gaps and an immutable metadata fingerprint. The native provider/runtime locations may be explicitly selected; missing installations are disclosed. It is intentionally not registered in the CLI, package, production catalog or UI yet.

The service reuses installed Starship's borrowed Starforge `detect_build_systems()` and `detect_config_files()` on metadata copies. Those detectors identify Compose/Docker files but do not extract service identities or OCI labels, so the adapter adds only static Compose/OCI extraction. It calls the installed Hermes `list_profiles()` against a temporary profile mirror containing only `profile.yaml` and `distribution.yaml`; actual credentials, config, skills, process state, wrappers and sessions are not copied. Before native inventory, the temporary files are reduced to bounded scalar-string fields and a boolean `description_auto`, so non-scalar YAML aliases cannot expand through the provider's string conversion. Native inventory decides profile identity, distribution and description. Original `SOUL.md` paths are references, not executable instructions; charter bodies are not emitted. Both a nonempty provider description and a charter are needed for `declared_candidate`; a default charter alone remains incomplete.

The metadata walk has explicit bounds: 100 roots, 300 directories, depth three, 1,000 named metadata files, 4 MiB total, 256 KiB per file and a three-second walk deadline. The native metadata subprocess has a separate configurable timeout capped at 15 seconds (`native_seconds`). Hidden/private/generated directories, links, byte limits, depth omissions and missing metadata remain visible through coverage. It does not contact any URL or container. An operating-system filesystem call can still be delayed by an unhealthy mount; inputs should be locally available indexed roots.

The cache key covers adapter bytes, provider source signatures, detector signatures, interpreter identity, selected source IDs/roots, profile folders, metadata contents and coverage. Repeated browsing reads the bounded metadata fingerprint and reuses the result; it does not repeat native inventory. Description, distribution, OCI or charter changes invalidate it. The cache must be outside inspected roots; unavailable runtime results are not published as a successful cache.

Interfaces are metadata only. Fixed provider templates distinguish `inspect`, `observe_status` and `ask_agent`; a service name or README cannot supply an arbitrary executable. Native profile routes use the installed Hermes launcher and selected profile home. Container routes require a literal container name and supported Hermes image or selected Dockerfile stage. Unknown/dynamic bindings omit callable templates. No generic structured `submit_work` declaration was found: the Observatory queue remains source evidence, not an invented automatically discovered route. Opening or searching a candidate does not execute any template.

[`tests/test_stars.py`](/Users/t/dev/navcom/tests/test_stars.py) proves two unfamiliar Compose workers and three native profiles: a declared charter, an auto-described charter and a missing charter. It also checks ordinary-repository/generic-assistant exclusion, selected non-agent build stages, source immutability, secret-field omission, malformed YAML, symlinks, input budgets, missing runtime/detectors and content-driven cache invalidation. ## Native Ask handoff: verified controls and limits

The installed Hermes CLI is an agent interface. Its [`chat` parser](/Users/t/.hermes/hermes-agent/hermes_cli/_parser.py:250) supports a single literal `--query`, classic CLI selection, quiet output and a maximum number of tool iterations. These are **not** an inference-only contract. Empty toolsets fall back to configured/default tools in [`cli.main()`](/Users/t/.hermes/hermes-agent/cli.py:15126); the installed toolset table has no built-in `none` set. `--safe-mode` drops user configuration, SOUL/rules, plugins and MCP, but does not remove all built-in tools and would discard the expert context. [`run_oneshot()`](/Users/t/.hermes/hermes-agent/hermes_cli/oneshot.py:128) explicitly enables YOLO and accepts hooks, so NavCom does not use it. The HTTP adapter constructs its agent with server-configured toolsets; this inspection did not verify a client-enforced tools-disabled mode or a configured endpoint.

[`navcom_star_chat.py`](/Users/t/dev/navcom/navcom_star_chat.py) therefore exposes a native handoff, not a simulated embedded answer:

- `prepare(center, question, cache_path, seconds=15)` refreshes the selected candidate with the existing discovery adapter and returns the exact question, provider identity, effects, metadata coverage and a review token. It does not contact a container, gateway or model.
- `handoff(center, question, cache_path, review_token=..., seconds=15)` repeats those checks and rejects changes to the question, candidate metadata, physical binding or installed provider identity. For a Compose expert, it also uses the existing read-only observer to require a running container with matching image, Compose file, directory and service, then pins the observed Docker context. A `DOCKER_HOST` override without a named context is explicitly unsupported. No chat command is executed by either function.
- Both return `handoff.argv`, `handoff.cwd`, `handoff.env` and a shell-quoted copy command. A trusted NavCom terminal launcher may use the freshly revalidated result only after the user's explicit Open in Hermes action. A review token detects stale inputs; it is not authorization by itself. Metadata-provided executable arguments and project wrappers are never used.

Native profile commands explicitly select even the default profile: a bare Hermes invocation can follow `active_profile`. Native `resolve_profile_env()` also verifies the exact destination before handoff, rejecting unusual nested homes that Hermes would redirect elsewhere. The question is one `--query=<literal>` argument so option-like text cannot be mistaken for Hermes' early profile selection. The installed interpreter runs with `-I -B`; a fixed NavCom entry-point shim pins the installed provider root before calling `hermes_cli.main.main()`. Ambient `PYTHONPATH`, `PYTHONHOME`, user-site imports and current-project Python modules cannot replace the reviewed provider. Parser, launcher, interpreter, adapter and relevant provider source identities are part of the review. The container's declared Hermes version is separate from the local installation; unverified local CLI flags are not imposed on it.

The shared UI/CLI effects state plainly that opening the native command sends the question, uses the expert's configured model/context/credentials/tools/hooks, may contact remote services or change files/submit work, and may save native session/skill data. Model readiness and visible arrival remain unverified. The native terminal owns interruption and output after handoff; NavCom does not claim to enforce a chat timeout or output cap. Preparation itself has a 15-second default/30-second maximum wall deadline for its process group, 2 MiB stdout and 64 KiB stderr bounds, a bounded metadata walk, and a 4,000-character question limit. Questions and responses are not written into the discovery cache.
